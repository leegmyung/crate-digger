# 서비스 적용 기획 — 신인 발굴 점수를 음악 스트리밍 서비스에 쓴다면

이 문서는 Gigle Research의 신인 발굴 점수를 **음악 스트리밍 서비스**에 적용하는 방법과, 효과를 검증할 실험 설계를 정리합니다. 근거 숫자는 모두 저장소 문서에서 가져왔고, 출처를 함께 적었습니다. 실험 설계의 전환율·효과 크기 같은 값은 **설명을 위한 가정값**이라고 표시했습니다.

## 1. 문제 정의

### 신인 노출이 왜 어려운가

| 원인 | 설명 |
|---|---|
| 인기 편향 | 추천은 재생·저장 기록이 많은 곡을 더 자주 보여 주고, 노출된 곡이 다시 기록을 쌓습니다. 기록이 없는 신인은 처음부터 순위가 낮습니다 |
| 콜드 스타트 | 막 나온 아티스트는 청취 기록이 거의 없어, 비슷한 취향을 근거로 추천하기 어렵습니다 |
| 사람 손의 한계 | 에디터·A&R이 공연·지원사업·매거진을 직접 훑는데, 출처가 흩어져 있고 양이 많습니다 |

**스트리밍 데이터만으로는 '아직 안 뜬' 신인을 찾기 어렵습니다.** 그래서 스트리밍 바깥의 신호(공연, 지원사업 선정, 매거진 소개)가 필요합니다.

### 이 프로젝트의 점수가 줄 수 있는 것

| 근거 | 숫자 | 출처 |
|---|---|---|
| 먼저 잡는가 | 정답(신인상·주요 신인 프로그램)을 받은 92팀 중 68팀이 정답 전에 우리 신호에 먼저 나왔고, 첫 신호는 정답보다 **중앙값 12.9개월** 먼저 | [SQL 결과 a02](sql/README.md) |
| 처음 보는 시점에서도 맞히는가 | 기준일 6개 교차 검증(가중치를 고를 때 안 본 시점으로 채점)에서 등급 가중 AUC 교차 검증으로 고른 가중치 **0.798** · v0 0.793 · 공연 수만 0.600 — 단순 기준(공연 수)보다 확실히 낫고, 손 공식끼리는 차이가 작음. 학습 모델(로지스틱 0.776)보다는 손 공식이 나음(정답 정리·보강, 같은 집안 규칙, 과거 기준일 유명 판정 제외, 앱과 같은 순위 규칙 적용 후) | [점수 교차 검증](score_tuning.md), [점수 모델 비교](score_model.md) |
| 상위 목록에 정답이 모이는가 | 상위 50팀 적중 합계 26팀(교차 검증, 기준일 6개 합계 정답 92행; v0는 23팀). 앱의 'v2 고정' 0.813은 기준일을 보고 고른 값이라 실제 기대치(0.80 안팎)보다 높음 | [점수 교차 검증](score_tuning.md), [방법론](methods.md) |

AUC는 정답 팀 하나와 아닌 팀 하나를 골랐을 때 정답 팀 점수가 더 높을 확률입니다(0.5 = 무작위). 단, **정답 팀 수가 적어(기준일마다 8~24팀) 숫자는 방향으로만** 읽어야 합니다.

## 2. 적용안 3가지

| | ① 큐레이터용 내부 도구 | ② '이번 주 떠오르는 신인' 플레이리스트 후보 추천 | ③ 개인화 추천의 신인 탐색 슬롯 |
|---|---|---|---|
| 무엇 | 지금 앱 그대로. A&R·에디터가 매주 보는 브리핑(후보 순위, 이유, 다가오는 공연) | 점수 상위 신인 중 에디터가 골라 매주 플레이리스트 구성 | 개인 추천 목록의 일부 칸(예: 20곡 중 1~2곡)을 취향에 맞는 신인 곡으로 채움 |
| 사람 판단 | 전부 사람 | 후보는 점수, 최종 선택은 사람 | 자동 (규칙·상한만 사람이 정함) |
| 필요한 데이터 | 지금 수집 데이터(공연·선정·매거진·발매) | + 서비스 안 아티스트·곡 번호 연결(아티스트 매칭) | + 사용자 청취 로그, 장르·취향 연결 |
| 운영 비용 | 낮음 (매일 자동 갱신 이미 있음) | 중간 (주 1회 에디터 검토) | 높음 (추천 시스템 연동, 실시간 서빙) |
| 위험 | 낮음 — 사용자에게 바로 노출 안 됨 | 맞지 않는 신인이 노출되면 플레이리스트 이탈 | 추천 품질 하락 → 청취 시간·만족도 하락 |
| 검증 방법 | 큐레이터 사용 빈도, 실제 기용한 신인 수 | A/B 실험 (3장) | A/B 실험 (3장) |

③은 **탐색·활용 균형**의 문제입니다. 이미 좋아할 곡(활용)만 보여 주면 신인이 묻히고, 신인(탐색)을 너무 많이 넣으면 만족도가 떨어집니다. 그래서 칸 수에 상한을 두고, 점수 상위 신인 중 사용자 취향(장르)에 맞는 곡만 넣습니다.

## 3. 실험 설계 (②·③)

| 항목 | 내용 |
|---|---|
| 가설 | 점수 상위 신인을 노출하면, 신인 곡을 끝까지 듣거나 저장하는 비율이 오르고 전체 청취 경험은 나빠지지 않는다 |
| 실험 단위 | **사용자**를 무작위 배정 (같은 사람이 두 화면을 섞어 보지 않게). 해시(user_id)로 고정 배정 |
| 대조군 | 지금 방식 (② 기존 플레이리스트 구성 / ③ 신인 칸 없음 또는 인기 기준 신인) |
| 처치군 | ② 점수 상위 신인으로 구성 / ③ 20곡 중 1~2칸을 점수 상위·취향 일치 신인으로 |
| 1차 지표 | 신인 곡 **30초 이상 재생률**, 신인 곡 **저장률** |
| 2차 지표 | **7일 재방문율**, 신인 아티스트 **팔로우 수** |
| 가드레일 | 전체 **청취 시간**, **건너뛰기율** — 나빠지면 효과가 있어도 중단 |
| 기간 | 최소 2주(요일 효과 두 번), 처음 며칠은 따로 봄 |
| 분석 | 두 비율 차이 검정, 사용자 단위로 집계(한 사람의 여러 재생을 독립으로 세지 않음) |

### 표본 크기 계산 예시 (가정값)

두 비율을 비교할 때 군마다 필요한 사용자 수:

```
n = ( z(1−α/2)·√(2·p̄·(1−p̄)) + z(1−β)·√(p0·(1−p0) + p1·(1−p1)) )² / (p1 − p0)²
    p̄ = (p0 + p1) / 2,  α = 0.05 → z = 1.96,  검정력 0.8 → z = 0.84
```

| 기준 전환율 p0 (가정) | 최소 검출 효과 | p1 | 군마다 필요한 사용자 |
|---|---|---|---|
| 20% (신인 곡 30초 재생률) | +1%p | 21% | 약 25,600명 |
| 20% | +2%p | 22% | 약 6,500명 |
| 5% (신인 곡 저장률) | +0.5%p (상대 +10%) | 5.5% | 약 31,200명 |

- **효과를 작게 잡을수록 표본이 크게 늘어납니다.** 효과를 1%p에서 2%p로 잡으면 필요한 사용자가 약 4분의 1로 줄어듭니다.
- **신규성 효과:** 새 칸이 처음엔 눈에 띄어 많이 눌릴 수 있습니다. 첫 1주와 둘째 주를 나눠 보고, 효과가 둘째 주에도 남는지 확인합니다.
- **다중 비교 주의:** 1차 지표 2개 + 2차 지표 2개를 각각 α 0.05로 보면 우연히 하나쯤 '유의'가 나오기 쉽습니다. 1차 지표를 미리 하나로 정하거나, 여러 개면 기준을 나눕니다(예: 3개면 α 0.05/3 → 첫 줄 예시는 군마다 약 34,100명).
- **미리 고정:** 가설·지표·표본·기간·중단 기준은 실험 시작 전에 문서로 고정하고, 결과를 보고 바꾸지 않습니다.

## 4. 지표 정의

가정한 이벤트 로그: `listen_events(user_id, track_id, artist_id, ts, ms_played, source)`, 배정표 `assignment(user_id, variant)`, 점수 상위 신인 목록 `rising_artists(artist_id, week)`.

| 지표 | 정의 | SQL로 계산하는 법 (한 줄) |
|---|---|---|
| 신인 곡 30초 재생률 | 신인 곡 재생 중 30초 이상 들은 비율 (사용자별 평균) | `AVG(IF(ms_played >= 30000, 1, 0))` — 신인 곡 재생만, 사용자별로 먼저 평균 |
| 신인 곡 저장률 | 신인 곡을 들은 사용자 중 저장한 비율 | 저장 이벤트가 있는 사용자 수 ÷ 신인 곡을 들은 사용자 수 |
| 7일 재방문율 | 실험 첫 노출 뒤 7일 안에 다시 접속한 사용자 비율 | 첫 노출 다음 날~7일 사이 재생이 있는 사용자 ÷ 노출 사용자 |
| 신인 팔로우 | 노출 기간 중 신인 아티스트를 새로 팔로우한 사용자 비율 | 팔로우 이벤트 중 artist_id ∈ 신인 목록 |
| 청취 시간 (가드레일) | 사용자당 하루 평균 재생 시간 | `SUM(ms_played) / COUNT(DISTINCT DATE(ts))` 사용자별 |
| 건너뛰기율 (가드레일) | 30초 전에 넘긴 재생 비율 | `AVG(IF(ms_played < 30000, 1, 0))` 전체 재생 |

**예시 SQL (BigQuery)** — ① 군별 신인 곡 30초 재생률

```sql
WITH rising AS (
  SELECT DISTINCT artist_id FROM `proj.ds.rising_artists`
  WHERE week = DATE_TRUNC(DATE '2027-03-01', WEEK(MONDAY))
),
per_user AS (                       -- 사용자 단위로 먼저 집계
  SELECT e.user_id, a.variant,
         AVG(IF(e.ms_played >= 30000, 1, 0)) AS play30_rate
  FROM `proj.ds.listen_events` e
  JOIN `proj.ds.assignment` a USING (user_id)
  JOIN rising r USING (artist_id)
  WHERE e.ts BETWEEN TIMESTAMP('2027-03-01') AND TIMESTAMP('2027-03-15')
  GROUP BY e.user_id, a.variant
)
SELECT variant, COUNT(*) AS users, AVG(play30_rate) AS play30_rate,
       STDDEV(play30_rate) / SQRT(COUNT(*)) AS std_err
FROM per_user GROUP BY variant;
```

② 군별 7일 재방문율

```sql
WITH first_seen AS (
  SELECT user_id, MIN(DATE(ts)) AS d0
  FROM `proj.ds.listen_events`
  WHERE source = 'rising_slot' AND ts >= TIMESTAMP('2027-03-01')
  GROUP BY user_id
),
came_back AS (
  SELECT f.user_id,
         MAX(IF(DATE(e.ts) BETWEEN DATE_ADD(f.d0, INTERVAL 1 DAY) AND DATE_ADD(f.d0, INTERVAL 7 DAY), 1, 0)) AS returned
  FROM first_seen f
  LEFT JOIN `proj.ds.listen_events` e USING (user_id)
  GROUP BY f.user_id
)
SELECT a.variant, COUNT(*) AS users, AVG(c.returned) AS return_7d
FROM came_back c JOIN `proj.ds.assignment` a USING (user_id)
GROUP BY a.variant;
```

③ 가드레일 — 군별 사용자당 하루 청취 시간·건너뛰기율

```sql
SELECT a.variant,
       AVG(u.ms_per_day) / 60000 AS minutes_per_day,
       AVG(u.skip_rate)          AS skip_rate
FROM (
  SELECT user_id,
         SUM(ms_played) / COUNT(DISTINCT DATE(ts)) AS ms_per_day,
         AVG(IF(ms_played < 30000, 1, 0))          AS skip_rate
  FROM `proj.ds.listen_events`
  WHERE ts BETWEEN TIMESTAMP('2027-03-01') AND TIMESTAMP('2027-03-15')
  GROUP BY user_id
) u
JOIN `proj.ds.assignment` a USING (user_id)
GROUP BY a.variant;
```

(재방문율은 대조군에도 같은 기준의 '첫 노출일'이 있어야 공정합니다. 대조군은 실험 배정일을 d0로 쓰거나, 같은 신인 목록의 곡을 처음 들은 날을 씁니다. 처치군에만 있는 노출 경로는 `source`로 따로 표시합니다.)

## 5. 단계별 출시

| 단계 | 내용 | 기간 (예) | 넘어갈 기준 (성공) | 멈출 기준 (중단) |
|---|---|---|---|---|
| 0. 내부 도구 | 큐레이터가 매주 브리핑 사용 (①) | 1~2개월 | 큐레이터가 매주 쓰고, 점수 상위 중 실제로 기용·검토한 신인이 생김 | 4주 동안 거의 안 씀 → 화면·이유 문구 개선 먼저 |
| 1. 소규모 실험 | ② 플레이리스트 또는 ③ 신인 칸을 사용자 일부(예: 1~5%)에 | 2~4주 | 1차 지표 유의하게 개선 + 가드레일 유지 | 가드레일 악화(청취 시간 감소·건너뛰기 증가)가 미리 정한 선을 넘음 |
| 2. 확대 | 배정 비율을 단계적으로 늘림 (10% → 50% → 전체) | 각 단계 1~2주 | 단계마다 같은 지표 확인, 신규성 효과가 사라진 뒤에도 효과 유지 | 확대 중 지표가 되돌아가면 직전 비율로 복귀 |
| 3. 운영 | 점수 갱신·출처 성적표를 매달 점검 | 계속 | 출처별 성적이 유지됨 (출처 재분류 제안 자동 확인) | 점수의 예측력이 기준선 수준으로 떨어짐 |

## 6. 한계와 윤리

| 주제 | 내용 | 대응 |
|---|---|---|
| 인기 편향을 다시 키울 위험 | 점수가 '이미 공연·매체에 자주 나온 팀'을 올리면, 그 안에서도 소수만 계속 노출될 수 있음 | 같은 팀 반복 노출 상한, 장르·지역 다양성 확인, 점수 상위 밖 신인도 일부 섞기 |
| '수상 = 성공' 정의의 한계 | 정답은 신인상·주요 프로그램이라 장르·심사 취향이 반영됨. 청취자에게 사랑받는 신인과 다를 수 있음 | 서비스 안에서는 청취 지표(재생·저장·팔로우)를 성공 기준으로 다시 정의하고 비교 |
| 표본이 작음 | 정답 팀이 기준일마다 8~24팀이라 점수 성능 숫자가 흔들림 | 정답 회차를 계속 모으고, 서비스 실험 결과로 다시 검증 |
| 데이터 출처 약관 | 공연·매거진·플랫폼 페이지마다 이용 약관과 수집 허용 범위가 다름 | 서비스에 쓰기 전에 출처별 약관·계약 확인, 공개 API 우선, 원본 데이터는 공개하지 않음 (지금도 원본 비공개) |
| 아티스트에게 미치는 영향 | 점수가 낮은 팀이 '가능성 없음'으로 읽힐 수 있음 | 점수는 노출 후보를 고르는 내부 참고값으로만 쓰고, 순위를 외부에 공개하지 않음 |

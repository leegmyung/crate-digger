# 사운드 지도 (씬 관계도) 데이터

같은 무대에 자주 함께 서는 팀들은 같은 '씬'에 있을 가능성이 큽니다. 공연 기록으로 팀과 팀을 잇고, 촘촘하게 이어진 무리를 **씬 묶음**으로 나눴습니다. 시각화는 앱이 하고, 여기서는 데이터와 만드는 규칙을 설명합니다.

- 만들기: `python3 scripts/build_scene_map.py` → `docs/lab/data/scene_map.json`
- 입력: `docs/lab/data/signals.csv`(공연 신호), `teams.csv`(이름), 최신 점수 스냅샷(`snapshots/<날짜>.csv`, 후보 순위)
- 공개 데이터만: 팀 키·이름, 공연장 이름, 숫자

## 만드는 규칙

| 단계 | 규칙 | 이유 |
|---|---|---|
| 1. 공연 고르기 | 기준일 전 1년, 발굴 역할 출처의 공연 신호, 공연장이 적힌 것 | 씬은 빨리 바뀌고, 검증된 출처만 씀 |
| 2. 잇기 | 같은 날·같은 공연장에 선 팀끼리 연결, 가중치 = 함께 선 횟수 | '같은 무대' = 같은 기획·같은 관객층 |
| 3. 큰 공연 빼기 | 출연 12팀 초과 공연(페스티벌)은 연결에서 뺌 | 모든 팀이 서로 이어져 지도가 뭉개짐 (1년 공연의 99% 이상이 12팀 이하) |
| 4. 묶기 | 라벨 전파: 각 팀이 이웃 중 연결 무게 합이 가장 큰 라벨을 따름. 무게는 함께 선 횟수의 세제곱, 동점은 사전순 | 외부 라이브러리 없이 매번 같은 결과. 세제곱은 '한 번 우연히 같이 선' 연결보다 '반복해서 같이 서는' 관계를 따르게 함 |
| 5. 정리 | 3팀 미만 묶음은 버림. 묶음마다 대표 공연장 3곳, 상위 후보 5팀(점수 순위), 허브 팀 5팀(묶음 안 연결 무게 합) | 작은 묶음은 씬이라 보기 어려움 |

**세제곱을 쓴 이유 (실측, 2026-11-27):** 횟수를 그대로 쓰면 홍대 공연장 팀 대부분이 한 묶음(926팀)이 됐습니다. 두 번 이상 같이 선 연결만 쓰면 묶음은 촘촘해지지만 지도에 남는 팀이 2,503팀 → 259팀으로 줄었습니다. 세제곱은 지도에 남는 팀 수(2,469팀)를 거의 그대로 두면서 가장 큰 묶음을 442팀으로 나눴습니다.

## `scene_map.json` 구조

| 칸 | 뜻 |
|---|---|
| `as_of`, `window` | 기준일, 공연을 본 기간(from~to) |
| `params` | 규칙 값 (큰 공연 기준 `max_event_teams`, 최소 묶음 크기 `min_community`, 내보내는 연결 최소 횟수 `min_edge_weight`) |
| `n_events`, `n_teams`, `n_links` | 쓴 공연 수, 연결된 팀 수, 연결 수 |
| `communities[]` | 묶음: `id`, `size`, `internal_links`(묶음 안 연결 수), `top_venues[]`(`venue`, `events`), `top_candidates[]`(`team_key`, `name`, `rank`, `score`), `hubs[]`(`team_key`, `name`, `links`) |
| `nodes[]` | 묶음에 든 팀: `team_key`, `name`, `community`, `degree`(연결된 팀 수), `rank`(점수 순위, 없으면 null) |
| `edges[]` | 두 번 이상 함께 선 팀 쌍: `source`, `target`, `weight`(함께 선 횟수) — 앱 시각화용으로 가볍게 줄임 |

## 한계

- 공연 기록이 많은 출처(인디스트릿)에 기대므로 그 출처에 잘 안 올라오는 씬(지역·힙합·전자음악)은 약하게 잡힙니다.
- 공연장 표기를 묶은 뒤의 이름을 쓰지만, '언플러그드 라운지'와 '카페 언플러그드 홍대점'처럼 주소가 다른 곳은 따로 셉니다.
- 라벨 전파는 묶음 수를 미리 정하지 않는 대신, 큰 묶음이 생기기 쉽습니다. 더 나누려면 묶음 1만 다시 라벨 전파를 돌리는 방법이 있습니다(다음 개선).
